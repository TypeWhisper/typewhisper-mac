# Regex dictionary sync, version 2

Mac and Windows use `dictionary:correction:regex:<pattern>` for regular-expression corrections. `<pattern>` is the unpadded Base64URL encoding of the original UTF-8 bytes. Do not trim, lowercase, fold accents, or normalize Unicode. `\d`, `\D`, `é`, `e`, decomposed `é`, and patterns with surrounding spaces are distinct. The `caseSensitive` flag changes matching behavior, not identity.

Terms and literal corrections keep their existing normalized version-1 IDs. A literal correction and a regex correction with identical original text can coexist. Changing a rule's mode or pattern changes its identity: publish the new entry and a tombstone for the previous ID.

Regex mode applies only to corrections. Ignore a stray `isRegex` flag on terms when importing, synchronizing, comparing, or deleting them. A term must never supply an inferred regex mode to a legacy correction with the same original text. Windows clears the flag at its dictionary import and sync storage boundaries, including fallback stores.

## Operations and older clients

Regex upserts and tombstones use operation `schemaVersion: 2`. The collection remains `dictionary`; upserts must contain a correction with `isRegex: true` and the matching exact-pattern ID. Version 2 is not accepted for other collections or literal entries. The package manifest remains version 1, and literal corrections, terms, snippets, and history keep their existing operation formats.

Existing clients accept only schema-1 operations, so they ignore the new regex operations rather than folding their IDs and overwriting different patterns. Older Mac clients can report these files as an unsupported schema. All devices that need to exchange regex corrections must be upgraded. Literal sync remains available to older clients.

## Migration

Resolve version-1 operations in their original namespace before migrating regex upserts. Map transmitted unencoded IDs for all dictionary payloads, including terms and literal corrections, to their canonical version-1 keys before resolving tombstones. An old tombstone or a later renamed/replaced entry suppresses every superseded version-1 correction upsert, whether literal or regex. A mode change must not restore both versions on a newly upgraded device. Record suppressed valid operations as applied too, so losing the newer operation file cannot resurrect a stale correction on that device. Surviving legacy regex upserts are mapped to exact-pattern IDs and republished in version 2 on the next sync. Local export versions advance to `dictionary-v3` so existing entries publish their current metadata once. Only newly applied version-1 operations request migration republishing; historical files must not make subsequent version-2 edits publish a duplicate operation.

Legacy tombstones do not target migrated version-2 identities, because a folded ID cannot distinguish `\d` from `\D`. For each pre-`dictionary-v3` local identity, recover its last synchronized mode and exact pattern from the winning version-1 operations already recorded as applied. Newly arrived remote edits must not change which pattern a local deletion targets. If that known regex still exists under its exact-pattern ID, withdraw the old folded ID without a tombstone, preserving the rule on older peers. If the regex was deleted, renamed, or changed to literal before the first upgraded sync, publish a version-2 tombstone for its previous exact ID; also publish the usual version-1 tombstone when the old folded ID is absent locally. This prevents another upgraded peer's version-2 upsert from restoring the removed regex. A known literal still gets its normal version-1 tombstone, including when the user changed it to regex before the first upgraded sync. Use an upgraded client to delete a migrated regex rule.

Before migrating each pre-`dictionary-v3` correction, require a readable, already-applied version-1 upsert whose entry timestamp matches that correction's stored export version. Resolve ties among those matching upserts. An operation with a different version is insufficient, even if it has a later timestamp: device clock differences can give an already-applied tombstone or older upsert a timestamp later than the actual synchronized local entry. Use the matching export version for mode repair and deletion identity too. If the required operation is missing or unreadable, postpone the upgrade sync before changing dictionary data or migration state and retry after the cloud provider downloads it. Unrelated missing IDs from pruned tombstones, malformed files, and Mac history operations that Windows does not support do not prevent migration when the required correction versions are available.

Validate that already-applied history structurally and match its stored export version without imposing current pattern or replacement limits. Older versions could accept data that the current import policy rejects, such as long literal replacements on Windows or unsupported regex patterns on Mac. Those historical entries must remain usable as migration evidence so they cannot block unrelated sync. New incoming operations still require the current validation checks.

If none of the package's readable operations has a previously applied ID and no operation file is unreadable or malformed, treat the package as removed or replaced. Republish the current local data, including unchanged snippets, without inferring old regex modes or exact regex deletion identities from unavailable history. Preserve known IDs so pending local deletions still produce their normal tombstones; withdraw a pre-v3 folded correction ID only when the local regex timestamp matches its stored export version. Otherwise retain the ID so a local change from literal to regex still deletes the old literal. Without history, a mode change cannot be distinguished from an edit to an existing regex: recovery can therefore remove the old rule on clients that have not upgraded, while upgraded clients retain the current version-2 regex. Keep previously applied IDs so old files that return cannot reapply stale operations. A fully unreadable package does not qualify for this recovery. When only part of the old package remains and required files were permanently deleted, the error message directs the user to choose a new sync folder, which resets local sync state and rebuilds from local data.

Before its first export, an upgraded Mac repairs regex modes that an older Mac dropped when receiving Windows version-1 operations. Repair requires a surviving version-1 regex operation already recorded as applied, its folded ID in pre-`dictionary-v3` local state, and a local literal with the same UTF-8 original, replacement, timestamp, case sensitivity, and enabled state. The repair retains the local entry's identity and usage count. Locally edited literals and literals exported by a version-2-capable client are not reclassified. Repair runs before publication so an old copy cannot be republished as an explicit literal, including when Windows has already published the version-2 rule.

Missing `isRegex` is different from an explicit `false`. A legacy update preserves a known local regex mode only for the exact same pattern and when it does not address a coexisting literal entry. Resolve this mode before validating the pattern, including whitespace-only regex rules. The preserved mode is republished once. New legacy entries without a mode default to literal. At equal timestamps, an explicit mode takes precedence over an absent field.

## Pattern portability

The shared identity and wire format do not make the regex engines identical: macOS uses ICU through `NSRegularExpression`, and Windows uses .NET regular expressions. Syntax accepted on one platform may be unsupported on the other. Both platforms skip incoming regex patterns that their engine cannot compile, before they can replace stored corrections. Empty patterns are rejected; whitespace-only regex patterns remain supported. Windows also enforces its catalog constraints: 160 UTF-16 code units and no literal CR or LF characters in patterns. Escaped newline patterns such as `\n` remain valid. Windows requires newly received correction replacements to be non-null and no longer than 10,000 UTF-16 code units; an empty replacement is valid, including when editing an imported rule. Use syntax supported by both engines for rules that must run on both platforms. Mac dictionary JSON imports reject invalid ICU patterns before inserting any entries, including disabled rules. Settings backup imports skip those rules and include them in the skipped count. Windows backup terms ignore a stray regex flag and retain normal trimming and duplicate detection. A Windows backup regex rule with the same exact pattern but different case sensitivity is an import conflict, not a second identity.

## Verification

Both repositories contain identical fixtures in their test `Fixtures/PremiumSync` directories:

- `regex-dictionary-identities-v2.json`: byte-exact IDs, case, accents, Unicode composition, spaces, and an emoji.
- `upsert-dictionary-regex-v1.json`: legacy migration input.
- `upsert-dictionary-regex-v2.json`: shared version-2 wire payload.

Sync tests cover independent rules, literal/regex coexistence, targeted deletion, preserved legacy mode (including whitespace-only patterns), one-time republishing and subsequent edits without duplicate publication, upgrades with already-synced state and partially downloaded or missing files, rebuilding removed or replaced packages while preserving local deletions and mode changes, clock differences, Windows catalog limits, incoming patterns unsupported by ICU, already-applied history outside current import limits, pruned unrelated tombstones and unsupported history operations, deletion/renaming/mode changes before the first upgraded sync, unencoded literal tombstones, and superseded literal or regex operations that stay suppressed after the winning file disappears.

The dictionary HTTP APIs include `isRegex` in GET responses. PUT and DELETE use `(original, isRegex)` as their identity; omitted `isRegex` means literal, so older API clients cannot update or delete a regex accidentally. Invalid regex PUT requests return HTTP 400. To change modes, delete the old mode and create the new one.
